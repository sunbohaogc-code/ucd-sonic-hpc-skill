# UCD Sonic HPC

A reference to the intended task is sufficient to start. Recover its launch command from project evidence. The user transfers files, prepares the Sonic environment, and submits jobs. Read [Sonic operations](references/sonic.md) for packaging, account discovery, resources, and result retrieval. Adapt explanations and commands to the user's language, shell, and familiarity with HPC.

1. **Confirm the task.** Read the conversation, README, approved design, configs, launch scripts, and available run records. Identify the actual entry point and effective arguments. Ask one focused question when an unresolved choice affects execution. Assume a fresh run, adding resume inputs when requested. Follow the project's scientific settings, naming rules, and approval requirements.
2. **Trace every input.** Follow project imports, cross-project helpers, configuration references, file readers, conditional reads, and relevant globs. Include metadata, indices, and split assignments. Verify required local inputs and any producer-to-consumer paths for stages running on Sonic. Resolve missing dependencies before calling the package ready. Each new deployment must include its required scripts, configs, and inputs, including any required artifacts from earlier experiments, without implicit dependencies on previous deployment directories. Any shared large datasets kept outside the package must be explicitly listed in the manifest and runbook with their Sonic paths.
3. **Prepare runnable files.** Create a Slurm launcher, runnable code and helpers, and required configs in the deployment layout. Reuse portable code and existing path overrides. Adapt deployment copies where needed. Check local absolute paths, case-sensitive names, working-directory assumptions, imports, and output destinations. Use Linux paths and LF shell scripts. Follow the reference's login-node rule for every Sonic execution path, including fallback and resume instructions. Allocate distinct destinations for fresh runs and smoke. Identify any shared inputs needed in those destinations. Resolve the user's account settings through the reference. Every full run requests END,FAIL emails to the user's confirmed address. Smoke tests disable notifications, including shared-launcher smoke commands.
4. **Build one upload archive.** Put archives, generated support files, staging, and bulk packaging temporaries in the matching local project or experiment, normally its hpc directory. Preserve required workspace subtrees under a task-specific top-level directory. Include all inputs, runnable files, a manifest, and a short runbook. Map every payload file's exact local source to its archive member and Sonic destination, with purpose, size, and SHA-256. Record code provenance. For a recorder that supports RUNRECORD_COMMIT, follow the reference to embed the packaged source commit in the launcher and verify it in the smoke record. Verify members, hashes, path coverage, and launcher syntax. Provide the archive's path, size, target, and filled scp upload command for the user's local shell.
5. **Prepare smoke and full execution.** Supply a bounded smoke test using existing task controls. Check the compute-node interpreter, required CPU or GPU resources, imports, data loading, and output writes. Keep smoke artifacts separate from production. Retain production parameters. Explain a substantive new smoke implementation under the project's rules when existing controls are insufficient. Write extraction, smoke, monitoring, full-run, and retrieval commands into the runbook with filled values or variables defined in the same block.
6. **Plan structured result return.** Collect this run's tables, figures, data products, logs, and run records with workspace-relative paths and checksums. Exclude checkpoints and temporary files from the default return. Choose an archive for many or large files or a structured download folder for a few small files. Generate remote result packages in the Sonic working area. Give filled scp commands, local project download destinations, verification and restore steps, and collision handling. Follow the reference for finalized logs and failed runs.
7. **Give the next actions.** Keep the initial chat to the local scp upload command, remote extraction and smoke commands, and any material blocker. Label the machine and shell for each block. Keep the detailed checklist in the package. Interpret the user's smoke outcome before giving the full-run step. At return, provide the download and local verification steps. State preparation, smoke, and production status according to available evidence. Execution stays under the user's control.
